Why Browsers Debated Deprecating SVG SMIL for CSS

The debate among browser vendors over deprecating Synchronized Multimedia Integration Language (SMIL) inside SVG in favor of CSS animations stemmed from redundant web standards, engine maintenance challenges, and shifting performance architectures. While SMIL provided powerful declarative animations tailored for vector graphics, emerging technologies like CSS Animations and the Web Animations API promised a single, unified approach to animating both HTML and SVG. Although major vendors like Google Chrome initially pushed to phase out SMIL in the mid-2010s, critical feature gaps and pushback from developers ultimately preserved its place in modern web standards.

Redundant Standards and Consolidation

When SMIL was integrated into SVG, CSS lacked the capability to handle declarative animations. Over time, the W3C expanded CSS to support transitions, keyframe animations, and transforms. Browser vendors recognized that maintaining two entirely separate declarative animation systems—SMIL for SVG elements and CSS for DOM elements—created unnecessary redundancy across the web platform. Consolidating all animations into CSS and the JavaScript-driven Web Animations API promised a more unified developer experience and a cleaner specification roadmap.

Engine Complexity and Maintenance Costs

From an engineering standpoint, SMIL implementations were notoriously difficult to maintain. The SMIL timing model relies on a complex state machine that dictates how animations begin, sync, loop, and resolve dependencies. In engines like WebKit and Blink, the SMIL codebase was largely isolated from the modern rendering and compositing pipelines. It generated a disproportionate number of bugs, crashes, and security vulnerabilities relative to its usage, leading browser engineers to advocate for its removal to reduce technical debt.

Hardware Acceleration and Performance

Modern browsers rely heavily on GPU-accelerated compositing pipelines to ensure smooth 60fps animations. CSS animations were designed and optimized to run off the main JavaScript execution thread, allowing transforms and opacity changes to render without triggering costly layout calculations. Conversely, SMIL was architected before modern compositing paradigms existed. Evaluating SMIL timing graphs and recalculating SVG DOM attributes frequently forced main-thread reflows and repaints, resulting in sub-optimal performance on resource-constrained devices.

Feature Parity Issues and Developer Pushback

In 2015, Google Chrome officially announced its intent to deprecate SMIL, advising developers to migrate to CSS animations and the Web Animations API. However, this proposal met immediate resistance from the web development community because alternative technologies lacked feature parity. Key SMIL capabilities could not be replicated natively in CSS, including:

  • Morphing Paths: Animating changes directly between complex SVG path data strings (d attribute).
  • Motion Along a Path: Animating elements along arbitrary vector paths using <animateMotion>.
  • Advanced Timing Controls: Native support for syncbases, event-driven triggers, and additive animations within self-contained SVG files.

The Resolution

Because CSS and the Web Animations API did not yet support path morphing or motion paths in a cross-browser, performant manner, forcing developers away from SMIL would break thousands of existing standalone vector assets. In 2016, Chrome suspended its deprecation plans. Browser vendors instead shifted focus toward improving underlying SVG architectures while standardizing missing features (such as CSS offset-path) to achieve parity naturally rather than forcibly removing SMIL. Today, SMIL remains natively supported across all major evergreen browsers.

How Android Parses SMIL in MMS Messages

This article provides an architectural overview of how the Android mobile operating system processes Synchronized Multimedia Integration Language (SMIL) within its native Multimedia Messaging Service (MMS) infrastructure. It traces the journey of incoming MMS data from raw Protocol Data Units (PDUs) through the internal SMIL parsing engines, explains the generation of the Document Object Model (DOM), details how media is mapped to user interface components, and highlights modern security and handling adaptations.

MMS Reception and PDU Extraction

When an MMS arrives on an Android device via a WAP Push message over cellular data, the telephony stack retrieves the binary payload. Android processes this payload using an internal parsing utility known as PduParser.

The MMS payload consists of multiple parts packaged according to the MIME multipart specification. One of these parts typically contains the SMIL control file with the MIME type application/smil. The PduParser decodes the binary PDU into a structured GenericPdu object (such as RetrieveConf), identifying individual parts by their headers, including Content-Type, Content-ID, and Content-Location.

XML Parsing and the SMIL DOM

Once the application/smil part is isolated, the operating system converts the raw byte data into a readable input stream for interpretation:

  1. Tokenization via XmlPullParser: Android uses an implementation of XmlPullParser (historically KXmlParser) inside its internal SmilParser class. This component reads the XML elements sequentially.
  2. Document Construction: As tags like <smil>, <head>, <body>, and <par> (parallel) are processed, the parser instantiates a W3C-compliant DOM tree. This is managed primarily through Android's SmilDocumentImpl classes.
  3. Layout and Region Mapping: The parser processes the <layout> section within the SMIL <head>. It extracts <root-layout> dimensions and individual <region> definitions, parsing attributes such as top, left, height, and width to determine where media items should be rendered.

Translating SMIL into UI Models

Android's MMS client does not natively render raw SMIL like a full web browser. Instead, it converts the constructed SMIL DOM into an internal presentation framework known as a SlideshowModel:

  • Slide Allocation: Each <par> (parallel) container represents an individual slide. The parser iterates through the children of each <par> element, identifying <text>, <img>, <audio>, or <video> tags.
  • Media Attachment Resolution: The src attribute of a media tag usually contains a reference matching the Content-ID or Content-Location of another part within the MMS PDU (e.g., src="image01.jpg" or src="cid:part1"). The parser links the specific visual or audio element to its raw binary data.
  • Timing and Duration: Attributes such as dur (duration) are read to dictate how long an individual slide remains visible during automated playback.

After the SlideshowModel is populated, the app binds the data to custom UI views—such as slide presenters or standard Android view layouts—to display the message sequentially or as a scrolling conversation item.

Security and Modern Implementation

SMIL parsing historically ran into major security challenges, most notably within media-parsing frameworks like Stagefright, where malformed SMIL files or companion media could trigger memory-corruption vulnerabilities. In response, modern Android updates heavily sandboxed media extraction, isolated telephony parsing, and added strict boundaries around XML entity handling to prevent injection attacks.

In modern implementations (such as Google Messages), complex SMIL layouts with custom positioning and transition timings are largely deprecated. The SMIL parser is primarily used to determine the sequential order of attachments and body text, converting the legacy markup into straightforward, linear chat bubbles or standard sequential slide decks.

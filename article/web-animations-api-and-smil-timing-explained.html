Web Animations API and SMIL Timing Explained

This article explores the conceptual relationship between the Web Animations API (WAAPI) and the timing algorithms originally developed for the Synchronized Multimedia Integration Language (SMIL). WAAPI serves as the modernized, scriptable evolution of SMIL's timing architecture, adapting its mathematical engine to unify CSS animations, CSS transitions, and SVG timing into a single, high-performance browser execution model.

The Shared Lineage of Web Timing

Before the Web Animations API, the web platform suffered from fractured animation architectures. CSS Animations and Transitions offered performant styling transitions via declarative syntax, while SVG relied on SMIL to handle complex, vector-based synchronization.

SMIL established a mathematically rigorous timing specification (SMIL Timing and Synchronization) designed to synchronize independent audio, video, and vector graphics across a common timeline. However, SMIL suffered from poor developer ergonomics, inconsistent browser implementation, and a lack of direct scriptable control.

The W3C designed WAAPI to extract the mathematical strengths of SMIL and rebuild them as an imperative JavaScript foundation. In essence, WAAPI is the standardized implementation of the SMIL timing algorithm exposed directly to the browser’s compositing and scripting engines.

The Hierarchical Timing Model

At the core of both specifications lies a multi-tiered system for translating a single source of truth—the passage of wall-clock time—into a normalized property update on an element.

In SMIL, timing flows through a hierarchical tree of time containers (such as <par> for parallel tracks and <seq> for sequential tracks) down to individual animated elements. Each node in the tree transforms the time passed down from its parent.

WAAPI retains this exact time-transformation model through three distinct conceptual layers:

  1. Timeline Time: The global reference point provided by the DocumentTimeline, equivalent to SMIL’s global document clock.
  2. Animation Time (Run Time): The local timeline created by the Animation object, taking into account playback rates, pauses, seeks, and reversions.
  3. Iteration Time (Active Duration): The normalized progress passed into an AnimationEffect (such as KeyframeEffect), calculating where the animation currently sits within a specific cycle.

Normalizing Time: The Math Behind the Curves

Both SMIL and WAAPI rely on deterministic mathematical projections to compute animation state. Neither system defines animations merely as frame-by-frame updates; instead, they define continuous functions where f(time) = state.

1. The Active Interval and Local Time

SMIL defined the active duration using parameters such as begin, dur, end, and repeatCount. WAAPI directly adopts these calculations using equivalent properties:

  • SMIL's begin maps directly to WAAPI's delay (and startDelay).
  • SMIL's dur maps to WAAPI's iterationDuration.
  • SMIL's repeatCount maps to WAAPI's iterations.

Both systems resolve these attributes into an active interval. If a timeline sits outside this interval, both systems evaluate a fill rule to decide behavior: SMIL’s fill="freeze" operates identically to WAAPI’s fill: 'forwards', freezing the target at the terminal frame of its active duration.

2. Time Space Transformation and Pacing

Once local time is determined, both engines calculate directed time and iteration progress:

  • Directed Time: If an animation alternates direction (SMIL's auto-reverse paradigms or WAAPI's direction: 'alternate'), the engine mathematically folds the timeline back upon itself during odd-numbered iterations.
  • Normalized Phase (0.0 to 1.0): The engine converts the current millisecond value into a fractional value representing progress through the current iteration.
  • Timing Functions: SMIL used calcMode="spline" alongside keyTimes and keySplines to bend this fractional progress. WAAPI adapts this directly into pacing functions and bezier-curve easings applied across keyframes.

Additive Animation and Accumulation

One of SMIL's most advanced characteristics was its capacity to dynamically layer and blend concurrent animations using additive="sum" and accumulate="sum". Traditional JavaScript animation frameworks historically struggled with this, frequently overwriting competing values.

WAAPI integrated SMIL’s exact compositing rules through the composite and iterationComposite options.

  • Composite Modes: Dictate how multiple independent animations affecting the same CSS or SVG property interact (replace, add, or accumulate).
  • Accumulation: Dictate whether successive iterations build upon the end value of the previous cycle or reset to the beginning, mirroring SMIL's accumulation algorithms.

Summary of Conceptual Alignment

WAAPI does not replace SMIL by inventing an entirely new timing mechanism. Instead, it codifies the mature, mathematically proven timing algorithms developed for SMIL into a modern API. By taking SMIL’s hierarchical time-transformation trees, normalized progress functions, and additive composition algebra, WAAPI provides a shared execution engine that drives both modern SVG and CSS animations in the browser.

SMIL Wallclock Scheduling: Leap Seconds and DST

Synchronized Multimedia Integration Language (SMIL) allows media elements to be scheduled against real-world time using wallclock timing syntax. This article explains how SMIL handles real-world temporal anomalies—specifically Daylight Saving Time (DST) shifts and leap seconds—by examining its reliance on ISO 8601 standards, the host operating system's clock, and timeline resolution mechanisms.

Wallclock Values in SMIL

SMIL defines real-world scheduling using the wallclock() timing syntax, which conforms to the ISO 8601 standard. Authors can specify absolute dates and times (e.g., wallclock(2025-06-01T09:00:00Z)), local times with offsets, or recurring daily/weekly schedules (e.g., wallclock(08:00:00)).

SMIL does not maintain an independent astronomical or calendar engine. Instead, the SMIL timing model maps these wallclock values to presentation time instances relative to the playback engine and the host environment’s system clock.

Daylight Saving Time (DST) Adjustments

When scheduling events with local wallclock times across DST boundaries, SMIL relies on the host platform's time-zone database to translate local time into absolute timeline points.

"Spring Forward" (Clock Jump)

During the transition to DST, local clocks move forward (typically from 01:59:59 to 03:00:00), effectively skipping an hour.

  • If a SMIL event is scheduled using an absolute local time that falls within the skipped hour (e.g., 02:30:00), the player resolves the time based on how the underlying platform parses invalid local times.
  • Typically, the event triggers immediately at the transition moment (03:00:00) when the clock advances past the target time, preventing missed triggers.

"Fall Back" (Clock Repeat)

During the transition out of DST, local clocks move backward, repeating an hour (e.g., repeating the hour between 01:00:00 and 02:00:00).

  • An ambiguous wallclock schedule that lacks a specific UTC offset presents two possible trigger moments.
  • Most SMIL implementations trigger the event on the first occurrence of the specified wallclock time and will not re-trigger during the repeated hour unless the schedule is explicitly marked as recurring.

Best Practice for DST

To eliminate ambiguity during DST transitions, schedules should specify exact UTC offsets (e.g., +01:00 or -05:00) or use standard UTC (Z) notation.

Handling Leap Seconds

Leap seconds are periodically introduced by the International Earth Rotation and Reference Systems Service (IERS) to synchronize Coordinated Universal Time (UTC) with Earth's actual rotation.

ISO 8601 Compatibility

The ISO 8601 standard allows the designation of a leap second using the 23:59:60 format. If a SMIL document explicitly specifies this value, a conforming XML/ISO parser can parse the string without throwing a syntax error.

Host Platform Dependency

SMIL engines execute on platforms that follow POSIX standards. Standard POSIX time cannot represent leap seconds natively; it handles them by either repeating the 59th second (23:59:59), applying Network Time Protocol (NTP) clock slewing (gradually slowing the clock over hours), or stepping the clock backward by one second.

Consequently, SMIL does not attempt internal leap-second compensation:

  • If the host OS steps the clock back by one second, SMIL’s internal clock comparison may detect that the current time briefly failed to advance, but presentation playback remains tied to its monotonic internal document timeline.
  • If NTP slews the clock, SMIL will not detect any discontinuity, and wallclock triggers will execute according to the smooth adjustment provided by the OS.

Presentation Timeline vs. Wallclock Time

SMIL maintains a strict separation between the document timeline (continuous presentation time that begins at document start) and the wallclock schedule (used purely to calculate synchronization points or trigger start/end times).

Once a wallclock event has been resolved to a concrete point on the document timeline:

  • Adjustments to the wallclock (such as a leap-second correction or manual time changes) do not alter the playback rate or pitch of currently running media.
  • Only future, unresolved wallclock events recalculate their trigger points according to the updated system clock.

Sync SMIL Audio Playback Over Local Wi-Fi Mesh

Synchronizing Synchronized Multimedia Integration Language (SMIL) audio playback across multiple mobile devices on a local Wi-Fi mesh requires a shared network timebase, a command distribution protocol, and precise client-side audio scheduling. Because SMIL coordinates temporal events based on a local timeline, devices must translate SMIL timing directives into absolute wall-clock timestamps synchronized across the mesh. By combining local clock synchronization, master-follower messaging, and audio buffer scheduling, multiple devices can play synchronized SMIL-orchestrated audio without perceptible latency.

1. Establish a Shared Network Clock

Standard Wi-Fi mesh networks introduce variable latency and jitter, making real-time "play now" commands ineffective. Instead, all devices must share a synchronized reference clock:

  • Precision Time Protocol (PTP / IEEE 1588) or NTP: Implement a lightweight PTP or Network Time Protocol (NTP) client on each mobile device. Designate one device on the mesh as the local master clock.
  • Offset Calculation: Each follower device continuously polls the master clock to calculate round-trip delay and local clock drift, maintaining a synchronized sub-millisecond network timestamp.

2. Translate SMIL Timelines to Absolute Time

SMIL schedules media relative to container elements (e.g., <seq> for sequential playback, <par> for parallel playback) and offsets (e.g., begin="0s"). To synchronize these events across devices:

  • Timeline Orchestration: When an action occurs (such as starting a playlist or seeking), the coordinator node converts the SMIL timeline offsets into future absolute timestamps (e.g., Current Clock Time + 500ms).
  • Deterministic Event Mapping: Instead of distributing individual playback triggers sequentially, the coordinator parses the SMIL document and maps every audio node to a synchronized schedule that each device executes independently against its local, synchronized clock.

3. Transport Playback Commands via UDP Multicast

Distribute commands across the local Wi-Fi mesh using a lightweight transport layer:

  • UDP Multicast or Broadcast: Unicast connections (like standard HTTP or TCP) can choke the mesh radio spectrum and produce staggered arrival times. UDP multicast sends a single packet to all listening devices simultaneously.
  • Command Payload: Transmit JSON or Protocol Buffers containing the target media URI, the target playback position, and the absolute execution timestamp.

4. Implement Pre-buffering and Scheduled Playback

Mobile operating systems introduce audio pipeline latency through decoding and hardware buffers. To prevent playback stutter and desynchronization:

  • Asset Caching: Pre-load all audio assets specified in the SMIL playlist into device memory before the target execution timestamp arrives.
  • Hardware Timestamp Scheduling: Utilize low-level audio APIs (such as AAudio/Oboe on Android or AVAudioEngine on iOS) to schedule audio frame playback precisely at the designated hardware clock cycle corresponding to the network timestamp.

5. Continuously Correct for Drift

Even when starting synchronously, hardware clocks in separate mobile devices run at slightly different speeds, resulting in cumulative drift over time:

  • Periodic Synchronization Pings: The master device broadcasts periodic timecode beacons matching current SMIL timeline positions.
  • Dynamic Audio Resampling: If a device detects that its local playback has drifted by more than 10–20 milliseconds relative to the master timestamp, it should imperceptibly adjust the playback rate (resampling by ±0.5% to 1%) rather than hard-seeking, maintaining phase alignment without causing audible audio clicks or pitch shifts.

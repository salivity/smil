How SMIL Validators Check Excl Priority Clashes

This article explains how Synchronized Multimedia Integration Language (SMIL) validators detect and evaluate overlapping priority clashes inside an <excl> time container. It breaks down the role of the <priorityClass> element, analyzes the peer and hierarchy attributes (peers, higher, and lower), and details the algorithmic checks validators use to catch runtime deadlocks, timing conflicts, and undefined interruption behaviors.

Understanding the <excl> Container Semantics

The <excl> container specifies that only one child element may play at any given moment. When multiple child elements have overlapping active intervals, the SMIL runtime must determine which element takes precedence, which element stops or pauses, and which element is deferred or discarded.

To manage these interactions, developers group media elements into child <priorityClass> elements. Each <priorityClass> defines rules through three core attributes:

  • peers: Defines how elements within the same priority class interact when they collide (values: stop, pause, defer, never).
  • higher: Dictates the fate of an active child in this class if an element from a higher-priority class begins (values: stop, pause).
  • lower: Dictates the fate of an element in this class if it attempts to start while an element from a higher-priority class is playing (values: defer, never).

Step 1: Parsing the Priority Class Hierarchy

A SMIL validator begins by parsing the syntactic structure of the <excl> block. Priority order is determined by document layout: <priorityClass> elements declared earlier in the XML tree have higher priority than those declared later.

The validator verifies:

  • Media elements belong to valid <priorityClass> definitions or default fallback buckets.
  • The peers, higher, and lower attributes contain valid enumerated values.
  • No contradictory syntax exists within local scope definitions.

Step 2: Temporal Graph and Active Interval Mapping

Once structural integrity is confirmed, the validator calculates the active begin and end intervals for each child element within the <excl> block.

By building a temporal graph, the validator maps points in timeline coordinates where two or more elements attempt to execute concurrently. These overlapping intervals trigger the conflict-resolution evaluation.

Step 3: Conflict Simulation and Rule Verification

When the validator identifies an overlapping segment, it evaluates the interaction against the explicit or default priority rules to detect invalid states:

  1. Peer-Level Clashes: If two elements in the same <priorityClass> overlap:

    • If peers="stop", the validator ensures the active element successfully terminates upon the second element's start.
    • If peers="pause", the validator confirms the first element has a valid pause/resume lifecycle and sufficient duration metrics to resume later.
    • If peers="never", the validator flags a potential dead-code warning if the second element can never be executed under standard playback conditions.
    • If peers="defer", the validator checks whether deferred playback violates container boundaries or unresolved synchronizations.

  2. Cross-Class Interruption Checks: If elements from distinct priority classes overlap:

    • The validator evaluates whether the higher attribute of the lower class aligns with the start conditions of the incoming higher-priority element.
    • The validator evaluates whether the lower attribute allows or drops execution if an incoming lower-priority element triggers while a higher-priority element is active.

Step 4: Deadlock and Cyclic Deferral Detection

The most critical functional check is identifying cyclic dependencies and indefinite queue buildup. If multiple elements defer to one another, or if recursive pause/resume behaviors occur, an playback engine can freeze.

The validator performs dependency-loop tracing on all defer actions across active intervals:

  • It traces the deferral queue to confirm every deferred item has a deterministic point where it can either resume, restart, or safely terminate.
  • It checks whether an element deferred past the end of the parent <excl> container duration causes an illegal state or clipped presentation.

Step 5: Emitting Validation Errors and Diagnostics

If the timing graph exposes ambiguous priorities—such as missing explicit rules for unclassified peers or impossible synchronization anchors—the validator reports precise diagnostic messages:

  • Unresolved Collisions: Instances where timing specifications force concurrent playback without defined preemption.
  • Starvation/Unreachable States: Elements configured with never that will consistently be suppressed by continuous higher-priority media.
  • Queue Overflows and Deadlocks: Cyclic deferrals that prevent the <excl> element from resolving its own lifecycle.

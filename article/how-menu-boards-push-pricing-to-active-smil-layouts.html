How Menu Boards Push Pricing to Active SMIL Layouts

Modern digital menu board systems push updated pricing to active SMIL (Synchronized Multimedia Integration Language) layouts without interrupting active screen playback or triggering full system reboots. This seamless update mechanism relies on decoupled content architectures, localized data feeds, real-time communication protocols, and dynamic web-based rendering layers that execute within the SMIL engine.

Decoupling Media Assets from Pricing Data

SMIL acts as an XML-based orchestration layer that defines screen zones, playback sequences, and media timing. In modern digital signage deployments, menu layouts separate static heavy media (such as background videos and food photography) from dynamic text elements (such as item names, calorie counts, and prices).

Instead of burning prices directly into static image files or video renders, the SMIL playlist references dynamic web widgets (HTML5/JavaScript) or structured text overlays within designated screen regions. The SMIL file maintains the layout structure, while the content layer remains data-driven and fluid.

Data Synchronization: WebSockets and Polling

When a price changes in a restaurant’s Point of Sale (POS) or Content Management System (CMS), the update is published via an API to the digital signage server. To push this data to the edge device playing the SMIL layout, the software uses one of two primary transport methods:

  • Persistent WebSockets or MQTT: The SMIL-compliant media player maintains an active, low-overhead TCP connection with the signage server. When a price changes, the server broadcasts an immediate push payload containing the updated stock-keeping unit (SKU) IDs and new price values directly to the player.
  • HTTP Polling / Manifest Checks: The player queries a remote JSON or XML endpoint at predefined intervals (e.g., every 30 to 60 seconds) to check for modified timestamps or revised price tables.

DOM Updates Within SMIL Rendering Engines

Most enterprise SMIL hardware players run an underlying browser engine (such as Chromium or WebKit) inside the media zones defined by SMIL <ref> or <body> tags.

When the local player receives the updated pricing data:

  1. The incoming data payload is parsed into local memory or written to a local data cache (such as IndexedDB or a local JSON file).
  2. A JavaScript event or state-management hook triggers inside the active HTML view layer.
  3. The Document Object Model (DOM) updates only the specific text nodes containing the changed prices.

Because only the text elements are re-rendered, the background animations, video loops, and surrounding graphics continue running smoothly without flickering, black frames, or visual pauses.

Local Caching and Offline Resilience

To prevent screens from displaying blank price fields during internet outages, menu board software systems enforce local data persistence. The SMIL player stores the latest retrieved pricing dataset on its onboard flash storage.

If network connectivity drops when a price update is initiated, the system queues the update on the server. The player continues displaying the most recent locally cached pricing until the connection is restored, at which point the queue flushes and updates the SMIL presentation immediately.

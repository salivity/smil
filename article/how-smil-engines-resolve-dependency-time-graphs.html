How SMIL Engines Resolve Dependency Time Graphs

Synchronized Multimedia Integration Language (SMIL) engines resolve complex, interdependent timing relationships by combining directed dependency graphs, iterative constraint propagation, and discrete-event simulation. Because SMIL supports dynamic triggers, syncbase-based relative timing, and circular references, engines cannot rely on a static linear timeline. Instead, they model temporal relationships as an active dependency network, dynamically computing valid begin and end intervals while continuously reacting to runtime events and resolving cyclic constraints.

The Syncbase Dependency Graph

At the core of a SMIL engine is a directed graph where nodes represent timing elements (such as media clips, parallel <par> containers, and sequential <seq> containers) and edges represent syncbase relationships (e.g., element B begins at A.end + 2s).

During the document compilation phase, the engine constructs this graph to map both parent-child hierarchical constraints and cross-element temporal dependencies. For purely declarative, non-cyclic timelines, the engine performs a topological sort on this directed acyclic graph (DAG) to determine the baseline order of interval evaluation.

Dynamic Instance List Evaluation

SMIL separates static time declarations from dynamic run-time evaluations using "instance lists." Every element maintains sorted lists of resolved begin and end times.

The evaluation algorithm follows these steps:

  1. Unresolved State Assignment: Elements without a deterministic start time remain in an unresolved state until their syncbase dependencies fire or yield concrete values.
  2. Current Interval Calculation: The engine evaluates the first valid pair of (begin, end) points from the instance lists that satisfies the element's duration, restart semantics, and boundary rules (such as min and max constraints).
  3. Pruning and Shifting: Outdated or superseded intervals are pruned. If an ancestor or syncbase changes, subsequent instances are shifted or marked dirty.

Forward Constraint Propagation

When an interval is established, altered, or terminated, the SMIL engine initiates forward constraint propagation:

  1. The modified element notifies all dependent nodes connected via outgoing edges in the dependency graph.
  2. Dependent nodes recalculate their instance lists based on the newly reported times.
  3. If a dependent node's active interval shifts, the change ripples downstream through recursive propagation or an evaluation worklist queue.

This iterative relaxation ensures that changes such as a video stalling, streaming delays, or user interactions immediately update downstream schedules without requiring a full document re-parse.

Cycle Breaking and Circular Dependency Handling

Complex SMIL schedules often introduce temporal cycles—such as element A starting when element B ends, while B starts relative to an event on A. To prevent infinite loops and deadlocks during constraint propagation, the SMIL specification defines strict cycle-breaking rules implemented via the following mechanisms:

  • Temporal Monotonicity (Past-Freezing): Once an interval has begun or completed, its past boundary becomes immutable. Circular dependencies cannot retroactively alter past instance times.
  • Causal Breakpoints: Engines track evaluation depth during graph traversal. If a dependency chain loops back to an active or currently resolving node within the same time step, the engine breaks the cycle by evaluating the dependency against the current or previous iteration's interval rather than recomputing the loop indefinitely.
  • Tear-Off State Tracking: When recursive dependencies occur via repeat cycles, new intervals are treated as distinct instances, unfolding the cycle over time rather than evaluating it as a static recursive constraint.

Discrete-Event Simulation Loop

For runtime execution, the engine couples the dependency graph with a discrete-event scheduler backed by a priority queue (min-heap). The queue stores scheduled state changes, such as interval endpoints, syncbase triggers, and scheduled DOM events.

At each execution step, the engine advances simulation time to the earliest event in the queue, applies the state transitions, triggers downstream re-evaluations across the dependency graph, and enqueues any newly generated instance times. This hybrid approach allows declarative timing trees and unpredictable interactive inputs to resolve deterministically within a single unified execution model.

SMIL vs HLS Variant Playlists for Adaptive Bitrate

This article compares Synchronized Multimedia Integration Language (SMIL) and HTTP Live Streaming (HLS) variant playlists for adaptive bitrate (ABR) streaming. It examines how each format functions within a streaming architecture, their structural and syntax differences, how they handle protocol delivery, and their current relevance in modern media workflows.

Architectural Role: Server-Side vs. Client-Facing

The primary difference between SMIL and HLS variant playlists lies in where they operate within the streaming pipeline.

SMIL is fundamentally a server-side configuration tool in modern streaming workflows. Media servers, such as Wowza Streaming Engine, use XML-based SMIL files internally to map multiple single-bitrate video renditions into a unified ABR group. The media player rarely reads the SMIL file directly; instead, the server reads the SMIL file to dynamically generate client-compatible manifests.

In contrast, an HLS variant playlist (often called a master playlist or multivariant playlist) is a client-facing manifest. The client-side video player fetches the .m3u8 variant playlist directly over HTTP. The player parses this file, continuously evaluates local network bandwidth and device capabilities, and requests the appropriate media chunks independently.

Syntax and Data Format

SMIL uses an XML structure governed by W3C standards. It defines media sources and their properties—such as system bitrates, video widths, and heights—using standard XML tags (<smil>, <body>, <switch>, <video>).

<smil>
  <head></head>
  <body>
    <switch>
      <video src="stream_high.mp4" system-bitrate="2500000" width="1920" height="1080" />
      <video src="stream_low.mp4" system-bitrate="800000" width="854" height="480" />
    </switch>
  </body>
</smil>

HLS variant playlists use the UTF-8 encoded extended M3U plain-text format, standardized by the IETF (RFC 8216). Rendition metadata is declared using specific tags such as #EXT-X-STREAM-INF, which pairs parameters like BANDWIDTH, RESOLUTION, and CODECS directly with the URI of a corresponding media playlist.

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=2500000,RESOLUTION=1920x1080,CODECS="avc1.4d4028,mp4a.40.2"
stream_high.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=854x480,CODECS="avc1.4d401f,mp4a.40.2"
stream_low.m3u8

Delivery Protocol and CDN Caching

SMIL was developed during the era of stateful, connection-oriented streaming protocols like RTSP and RTMP. Because RTMP and RTSP maintain dedicated server connections, SMIL served as an instruction set for the server to switch streams mid-session. These legacy protocols do not cache effectively across standard Content Delivery Networks (CDNs).

HLS variant playlists were purpose-built for stateless HTTP delivery. The variant playlist references sub-playlists, which point to segmented media files (TS segments or fragmented MP4s). Because every request is a standard HTTP GET, variant playlists and their associated media segments can be easily cached at the CDN edge, allowing ABR streaming to scale to millions of concurrent viewers without overloading origin servers.

Modern Implementation and Coexistence

SMIL is no longer used as an end-to-end delivery mechanism for consumer playback. Native players in iOS, Android, web browsers, and smart TVs do not parse SMIL for ABR video playback.

Instead, SMIL and HLS variant playlists often coexist in hybrid enterprise architectures. An engineer may maintain a single SMIL file on an origin server to define bitrate ladders and dynamic stream names. When a client requests an ABR stream, the origin server reads the SMIL file and automatically converts those parameters into an HLS variant playlist to deliver to the client.

How to Prevent XXE Attacks in SMIL Parsers

Synchronized Multimedia Integration Language (SMIL) is an XML-based standard used to describe multimedia presentations, rich media, and Multimedia Messaging Service (MMS) payloads. Because SMIL relies on standard XML parsing engines, it inherits severe security vulnerabilities if the underlying parser resolves untrusted XML External Entities (XXE). This article outlines the specific parser configurations, validation techniques, and network defense measures required to protect SMIL parsers from XXE-based data exfiltration, local file disclosure, and Server-Side Request Forgery (SSRF).

1. Completely Disable DTD Processing

The most robust defense against XXE attacks is disabling Document Type Definitions (DTDs) entirely. SMIL files generally do not require custom DTDs to define multimedia layouts or timing. By instructing the XML parser to reject any <!DOCTYPE> declaration, external entity injection is neutralized before it can be processed.

  • Java (DocumentBuilderFactory, SAXParserFactory): Set the feature http://apache.org/xml/features/disallow-doctype-decl to true.
  • C/C++ (libxml2): Do not pass flags that expand entities or load external subsets, such as XML_PARSE_NOENT or XML_PARSE_DTDLOAD. Keep these options turned off by default.
  • Python (lxml): Set resolve_entities=False and load_dtd=False during parser initialization, or use the defusedxml package.

2. Disable External Entity and Parameter Entity Resolution

If an application requires DTD processing for schema validation, you must explicitly disable the fetching of external general entities and external parameter entities. This prevents an attacker from using SYSTEM or PUBLIC identifiers to load local files or remote resources.

  • Set http://xml.org/sax/features/external-general-entities to false.
  • Set http://xml.org/sax/features/external-parameter-entities to false.
  • Set http://apache.org/xml/features/nonvalidating/load-external-dtd to false.

3. Restrict Network Access During Parsing

Attackers frequently leverage XXE in media formats to trigger out-of-band (OOB) connections to attacker-controlled servers or scan internal infrastructure.

  • Parser-Level Network Blocks: If using libxml2, enable the XML_PARSE_NONET flag, which completely forbids network access for fetching external DTDs or entities.
  • Custom Entity Resolvers: Implement an empty or restrictive EntityResolver (or URIResolver). If the parser encounters an external resource identifier, the custom resolver should immediately return an empty input stream or throw an exception rather than making a network call.

4. Mitigate XML Entity Expansion (Billion Laughs Attack)

Even without external file access, nested inline entities can cause exponential memory consumption, leading to a Denial of Service (DoS). Secure the SMIL parser by limiting entity expansion:

  • Enable the secure processing feature (XMLConstants.FEATURE_SECURE_PROCESSING in Java) to impose hard limits on entity expansion depth and total entity counts.
  • In C-based libraries, leverage built-in recursion depth limits, ensuring the parser runs on an updated version with entity expansion guards (such as modern versions of libxml2).

5. Enforce Strict Input Validation and Pre-Parsing Filters

Before passing untrusted SMIL markup to the XML engine:

  • Pre-Check File Signatures: For protocols like MMS, scan raw incoming data streams for suspicious strings like <!DOCTYPE or <!ENTITY before initializing the parser. If custom DTDs are not part of the business specification, reject payloads containing these tokens immediately.
  • Schema Validation: Validate the SMIL structure strictly against local, pre-compiled XML schemas (XSD). Never allow the parser to fetch remote XSD or DTD definitions referenced in the input payload.

6. Sandbox the Parsing Environment

Apply defense-in-depth principles to limit the impact if a parser vulnerability is exploited:

  • Least Privilege: Run the SMIL parsing process under an unprivileged user account with read-only access to necessary binaries and zero access to sensitive directories (such as /etc, configuration directories, or cloud credential stores).
  • Egress Filtering: Restrict outgoing network traffic from the media-rendering engine using firewall rules or container network policies, preventing any unauthorized outbound HTTP, HTTPS, or DNS connections.
